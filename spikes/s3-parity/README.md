# Spike S3-LITE — Parity toolchain (Node vitest vs real browser engine, to 1e-9)

## Question

Does a pure TypeScript metrics function run IDENTICALLY under Node (vitest) and in a real
browser engine (via Playwright), to 1e-9, over the Chapter 4 Example A and Example B logs?

## Method

- `stats.ts`: pure functions `mean()`, `sampleStandardDeviation()`, and
  `netWpmFromLog(log, target)` where net WPM = (correct characters in final text / 5) / minutes
  and minutes come from the log's first-to-last accepted-keystroke span (`/60000`). Also parity
  probe helpers: `rawWpmFromLog` (printable keystrokes / 5 / minutes),
  `keystrokeAccuracyFromLog` (correct-at-landing / total printable keystrokes),
  `interKeyIntervals`. No DOM, no imports beyond node builtin types.
- `logs.ts`: Example A (§4.2: `the cat sat`, 11 evenly spaced keydowns, 0–5454 ms) and Example B
  (§4.3: same scenario plus x mistyped for c, Backspace, c retyped; correction adds ~400 ms,
  last keystroke 5854 ms) reconstructed exactly per the chapter tables, in the KeyEvent contract
  shape; each reconstruction choice is documented in the file (chapter lists keydowns only →
  `type: "down"` entries, no keyups; `code` values per US layout; mods false; repeat false;
  isTrusted true; chapter's exact `t` values).
- `vectors.ts`: the derived parity-vector assembly, used verbatim by BOTH runtimes (so the
  assembly code is under parity too).
- Node side: `parity.node.test.ts` (vitest) asserts the values against independently written
  fraction arithmetic (not calls back into stats.ts) and writes `parity.expected.json` — the
  transfer artifact consumed by the browser spec (documented choice; the package script `test`
  chains node → build → browser).
- Browser side: `parity.browser.spec.ts` loads `page.html`, which imports the tsc-compiled ES
  modules (`stats.js`, `logs.js`, `vectors.js`). file:// was attempted first; Chromium
  CORS-blocks ES module fetches from file:// origins, so the spec falls back to a throwaway
  localhost static server (the mechanism actually used is recorded in the test output). All six
  values per log are compared browser-vs-node at ≤ 1e-9.
- Purpose framing: this proves SHARED CODE RUNS IDENTICALLY IN BOTH RUNTIMES. The full M1-11
  parity harness over all fixtures comes later, in packages/engine.

## Result

PASS — LAB PROXY (Chromium headless only): browser === node to 1e-9; measured maxAbsDiff = 0
(bit-identical) for all 12 compared values. LAB PROXY (Chromium only) — Firefox/WebKit
PENDING: browser downloads failed (CDN 30 s timeouts); retry next session. file:// ES module
loading is blocked in Chromium (CORS, null origin) — localhost fallback used; this does not
weaken the parity claim (the same compiled bytes are served and evaluated).

## Risks

- Chromium-only run: Firefox/WebKit engines are unverified (download failures). IEEE 754
  basics plus correctly-rounded `Math.sqrt` are expected to match, but that is exactly what
  this spike exists to check — re-run when downloads succeed.
- The file:// → localhost fallback means a file://-only harness (if ever required) would need
  inlined/bundled scripts in Chromium.
- This proves runtime parity for a small function set over two logs, not the full 40-fixture
  catalog (M1-11 scope) and not server-side recompute parity.
- stats.ts definitions follow the typing-metrics-spec skill; raw/accuracy here are sanity
  probes — the engine package owns the real metrics and the modelVersion rules.
